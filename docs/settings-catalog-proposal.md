# 分区开关与联机配置

已按确认的第四版分区实现 78 个独立设置。按最新界面要求取消全部批量开关，保留分区折叠和逐项开关。以下是功能清单与实现边界；编译和独立配置检查已通过，游戏内界面、旧存档、Steam 重启及双端联机尚待实测。

## 通用行为

| 项目 | 规则 |
| --- | --- |
| 开关粒度 | 卡牌、遗物、事件及原版调整均保留独立开关；分区只负责折叠与归类 |
| 默认值 | 新设置默认开启，延续当前 Mod；迁移已有三个开关的用户选择；旧事件离开开关的值作为三个事件独立开关的初始值 |
| 生效时间 | 保存立即完成，实际效果统一重启游戏后生效 |
| 列表 | 全部 / 当前生效 / 待重启；显示已启用、已关闭、待启用、待关闭 |
| 快捷操作 | 不提供全开 / 全关及全局批量操作，用户逐项调整 |
| 原版调整关闭 | 恢复对应原版行为与说明；不逆转旧存档已经发生的永久变化 |
| 新增内容关闭 | 阻止之后从常规获取入口获得；保留旧存档所需的模型和已有物品的运行能力 |
| 联机 | 新增入房配置一致性校验需求：不一致时拒绝加入并在界面显示差异；检查方案见文末，不自动覆盖玩家配置 |

## 分区与逐项开关

界面使用默认收起的折叠分区，侧栏只显示简短名称。展开后保留角色 / 先古之民小标题与逐项开关，移除全部批量按钮和「更多操作」栏。单项名称不拼接状态，说明区显示状态和效果。顶部以下拉控件筛选，无匹配项的分区隐藏；重启按钮仅在存在待应用改动时显示。

### 配置变更后的重启入口

- 每次修改开关后，在最后操作的选项下方显示一处「重启游戏」按钮；顶部仍保留入口。提示不会为每个待生效项重复展开，撤销全部差异后自动隐藏。

- 设置页比较保存值与本次启动有效值；有差异时显示「配置已保存，重启游戏后生效」及「立即重启」按钮。全部撤销到有效值后取消提示。
- 本地 RitsuLib 0.6.2 设置接口提供 `AddButton` 与 `WithEntryVisibleWhen`，可以承载按钮及条件显示；已查接口文档未发现直接重启游戏的封装，不将其描述为已确认的 RitsuLib 功能。
- Godot 4.5 提供 `OS.SetRestartOnExit(true, OS.GetCmdlineArgs())`。确认 Mod 配置持久化成功后，再设置退出重启标记并调用原版 `NGame.Instance.Quit()`；不要在玩家仅修改配置时设置重启标记，避免正常退出也意外重开。
- `NGame.Quit()` 会保存游戏设置、偏好、进度与档案并退出，但不等于保存当前对局。仅在主菜单且未处于联机房间时提供立即重启；对局或房间内提示先按原版流程退出到主菜单。
- 该 Godot 接口支持桌面导出程序，不适用于编辑器内运行、移动端或 Web。Steam 下退出、自动重开及启动参数保留仍需真实验证，尚未执行重启。
- 参考：[Godot 4.5 OS.set_restart_on_exit](https://docs.godotengine.org/en/4.5/classes/class_os.html#class-os-method-set-restart-on-exit)、[RitsuLib 设置文档](https://sts2-ritsulib.ritsukage.com/guide/mod-settings)、`D:/Game/Sts2Code/src/MegaCrit.Sts2.Core.Nodes/NGame.cs` 的 `Quit()`。

## 联机配置检查

### 生效时机的源码核查

当前全量配置方案仍建议保留重启后生效，原因是现有实现包含缓存和对象初始化阶段的改动；并非设置 UI 或 Harmony 天生要求每次重启。

- `CardPoolModel.AllCards` 缓存 `GenerateAllCards` 与 Mod 内容合并后的结果，`AllCardIds` 也缓存；该类型虽有 `InvalidateCardCache`，但仅清理卡池不足以刷新所有卡牌模型。
- `CardModel.Keywords` 和 `DynamicVars` 首次访问后缓存，`DeepCloneFields` 会复制关键词及动态数值；`ModelDb.Card<T>()` 返回全局模型库中的对象。因此给 `CanonicalKeywords` / `CanonicalVars` 补丁加配置判断，不会自动更新已经生成的缓存，不能假定重新开局就足够。
- 现有刀舞补丁修改 `CanonicalKeywords`，稀有度补丁则修改 getter；若直接热切换，可能出现稀有度更新而消耗词条仍沿用旧缓存的混合状态。
- 事件离开选项在生成事件选项时读取配置，源码上可在下一次生成选项时生效，无需因这一项单独重启；已打开的事件不会自动重建。感染棱柱同样涉及入场和行动状态机生成，切换不能重建已在战斗中的对象。

联机一致性检查只证明双方报告的有效设置一致，不证明双方内存里的旧模型、卡池和已生成对象一致。若未来取消重启要求，需要另外实现完整的缓存刷新与配置应用边界，并验证主菜单修改后开新局等流程；本轮尚未完成这些工作，不承诺全量热切换。统一重启生效是当前全量方案的实现选择，不是每一项设置都存在不可绕过的重启限制。

保留原版全部联机检查与报错流程，只注入本 Mod 的配置一致性检查及专属错误类别「Mod 配置不一致」。该错误接入现有入房失败和弹窗流程，显示相关配置差异；其余错误完全交回原版处理。

| 场景 | 处理 |
| --- | --- |
| 加入房间，配置一致 | 继续原版加入流程 |
| 加入房间，配置不一致 | 阻止本次加入，在加入者界面显示不一致项目、房主值和本人值 |
| 已保存但尚未重启 | 比较本次启动实际生效的玩法配置，不以尚未生效的选择判定一致 |
| 纯显示设置不同 | 不参与玩法配置比较 |

游戏版本、Mod 缺失、连接失败、超时及其他异常沿用原版检查、分类、断连和提示行为；不拦截后统一改写为配置错误，也不另建通用错误处理系统。仅确认双方配置不同的情况使用新增的 Mod 专属错误类别。

实现包含必要的配置交换与比较，以及专属错误在现有失败流程中的识别和文案映射。配置交换遇到连接失败或超时时沿用原有错误路径，不误报为配置不一致，也不误判为校验通过。复用原有失败清理和弹窗，不增加配置同步、存档配置管理等无关功能。错误使用 `BalanceConfigMismatchInfo : ConnectionFailureExtraInfo` 承载，复用原版 ModMismatch 分支清理连接；弹窗仅识别本 Mod 的子类型，不修改原版枚举。
